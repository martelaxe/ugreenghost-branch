# Before You Move

# Goal

Help a NAS owner review a proposed change before acting. Show what references and possible roles were found, what they mean for the particular change, and what remains unchecked. The outcome is a read-only, source-backed decision preview, not a safety certificate or a complete dependency graph.

# Required input

Use when the user wants to move, rename, delete, or consolidate selected files or folders, or asks what a proposed change might affect. A short request is enough to begin. Obtain the actual target and intended change, the proposed destination or name when needed, and the folders authorized for inspection. Do not guess paths, automatically inspect other shares, or treat access permissions as the owner's consent. Ask only for missing essentials. If a target or potential reference is outside scope, request authorization instead of reading it. For consolidation ask which copies and intended action; do not treat matching content as proof that either copy is disposable.

# Orchestration

These examples illustrate syntax only. Before each call, construct its instruction with the real authorized paths, requested limits and actual completed upstream evidence; never send a generic example as the complete request.

`delegate --target file-agent --instruction 'Find actual files within the authorized scope for the proposed change.'`

`delegate --target document-agent --instruction 'Assess actual returned documents for references to the target.'`

`delegate --target knowledge-agent --instruction 'Seek supporting and contrary evidence for the unresolved impact.'`

1. Establish authorized scope and exact change. Use the **impact** flow for an individual move, rename or delete; use **copy-role comparison** only if the user identifies two or more copies to consolidate. No unrequested broad deduplication.
2. Delegate scoped discovery to `file-agent`, using a bounded search. Default to at most 50 returned paths and 20 selected documents unless the user requests stricter limits; these are requested limits, not proof the platform enforces them. Prioritize exact paths, relative references and likely project manifests, then possible name matches. Inspect returned candidates only. If the target cannot be established, do not assert target-specific effects.
3. Ask `document-agent` to examine selected candidate documents for references to the actual target and the consequence of the proposed change. Distinguish direct references from plausible name matches, historical mentions, unrelated matches, and unknown runtime use. Resolve relative paths only with sufficient returned context. Ask for paths and excerpts; do not invent them. If a specific material question remains and authorized evidence could answer it, ask `knowledge-agent` to seek both supporting and contrary evidence. Empty results do not establish absence.
4. In copy-role comparison, request hashes for actual authorized candidate paths when useful. Label matching hashes as evidence of byte equality at check time, not semantic interchangeability, app independence, backup status, or safety to delete. Separately report evidenced roles and unresolved dependencies for each copy.
5. Produce the decision preview described in the references. Identify observed facts, inferences, unknowns, relevant source paths and available excerpts. Give one safe next step appropriate to the findings, not a blanket declaration that the action is safe. Report actual scope, limits, observed results, skipped/inaccessible material, and unknown coverage. If no impact is found, state only that none was found in reviewed material.

On `failed` or `cancelled`, stop that branch and preserve any reliably returned partial evidence without claiming success. ### references/evidence-and-output.md
# Evidence and decision preview

Preserve each actual source path or stable identifier and excerpt if returned. Distinguish exact references, inferred consequences, contrary evidence and unresolved possibilities. Do not manufacture excerpts, file counts, paths, timestamps, approval states or missing source evidence. Match the requested paths to the expert's actual returned results; if correspondence is unclear, mark it unknown.

Report only counts supported by the completed returned inventory or explicit per-file results. State selected sources separately from discovered sources; a selected document is not successfully read unless supported by a completed result. If the listing meets a cap, is inaccessible, truncated, returns a partial state or does not establish completeness, report scope as incomplete or unknown. Do not assume pagination or declare all files checked. Runtime applications, external shares, unreadable files and later changes are outside the observed evidence unless explicitly supported.

## User-facing output

1. **Proposed change:** actual target and intended action; no action executed.
2. **What may be affected:** at most three prioritized evidence-backed relationships, with source paths and actual excerpts when returned; clearly label direct references versus interpretation.
3. **Copies and roles, if requested:** for each selected copy, give the actual path, its role supported by source evidence, any observed hash comparison, and what is unknown. A hash cannot establish permission to delete.
4. **What is unknown:** ambiguity, inaccessible/missing sources, unknown application usage, missing coverage, partial results and relevant scope limitations.
5. **Next safe step:** name the particular file, relationship or user decision to verify. If an excluded area could answer it, ask for targeted authorization or for the owner to supply evidence; if unavailable or declined, leave the question unresolved. Do not certify a move/deletion as safe.
6. **Coverage and state:** authorized roots, requested limits and actual counts or identifiers only if available; reviewed versus not reviewed; completed/partial/waiting/failed/cancelled as appropriate.

When no connection is substantiated, explicitly say none was found in the reviewed material. That is not proof of absence. If exact paths or evidence are not returned, say so rather than citing guessed locations. Mark claims of app breakage as uncertain unless actual evidence establishes the relevant behavior.

### references/workflow.md
# Workflow and decision rules

All steps are read-only. User-supplied paths and scope are necessary inputs, not permission to search elsewhere. Ask the owner to resolve ambiguous target identity before evaluating that target. Do not read the contents of excluded files even when their names appear in authorized records.

## 1. Focus the investigation

Record the selected item, change, actual destination/new name if relevant, authorized search roots and constraints. Check the target with `file-agent` using documented `ug-filesystem` operations and ask it to return observed paths, limits, failures and potential reference-bearing candidates. If target is missing or inaccessible, report the uncertainty; do not state that the intended change will or will not break anything. For a folder, name the scope of returned contents rather than assuming every descendant was examined.

## 2. Find and resolve references

Ask `file-agent` for a bounded candidate inventory based on target path, filename and user-supplied contextual clues. Ask `document-agent` to read actual selected candidates and distinguish:

- **Exact or path-resolved reference:** evidence explicitly points to the target, subject to supported path context.
- **Ambiguous match:** a matching filename or phrase does not identify the target uniquely.
- **Historical/context-only:** source discusses an item or old project without establishing current use.
- **Contrary evidence:** source qualifies, replaces, or rules out an apparent dependency.
- **Unknown:** document not read, result unavailable, incomplete scope or live application behavior not observable.

Request exact source paths and excerpts where returned, preserve the raw substance of the evidence, and distinguish a quoted reference from its interpretation. Do not equate a real quote with proof that an application will fail. Only describe a consequence as observed when an actual returned record supports it; otherwise label it conditional or unknown. Seek a narrow contrary check via `knowledge-agent` only when it may change the proposed action. Do not falsely claim all references or applications have been examined.

## 3. When comparing copies

On user request, check explicitly identified authorized copies. If child results provide hashes for each, compare those hashes as observations at that time. Equal SHA-256 is strong evidence of matching bytes, not proof of same role. Different hashes do not establish which version is newer or correct. Inspect returned records for each copy's role; absence of a reference in the bounded scan does not prove no role. If a source indicates the same content is used by two projects, explain the specific source-backed relationship rather than treating either path as redundant. Do not assume inaccessible or unselected copies are covered.

## 4. Prepare the decision

Rank actual directly supported possible consequences above name-only matches; put unknowns beside the relevant claim. Present an appropriate next action, such as verifying an ambiguous reference or asking an application owner. If the desired change conflicts with an observed reference, advise preserving the item until the user resolves the conflict. If a known excluded area could answer a material unresolved question, identify that area only as actually described and ask whether the owner authorizes a targeted review or can supply the relevant evidence. Do not inspect it until authorized. If the owner declines or the area is unavailable, keep that question unresolved. Never execute a change. A repeat request starts a fresh check: do not assume old results remain current, a persistent cache exists, or a previous result proves today's state.
