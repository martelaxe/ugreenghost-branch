# Discovery Engine V2 — local research architecture

1. **Inventory and read:** a research-only local adapter records paths discovered under the chosen workspace, selected paths, successful reads, unsupported/skipped paths, errors, byte limits and truncation. Its conservative missing-reference scan recognizes explicitly written PDF names; it is not a general document dependency resolver. Even a locally complete selection does not prove the wider archive has no missing or inaccessible sources.
2. **Capture candidates and evidence:** store untouched copies of the candidate proposal, claims, blockers, citations and original text. A later completed review may contribute additional evidence without replacing the original candidate; each additional quote is checked against retrieved text. Evidence records link material claims to paths/excerpts and record retrieval, exact-match status, asserted relationship (`supports`, `contradicts`, `related`) and limitations. Claims and evidence are local research data structures, **not UGREEN result fields**.
3. **Review:** accept a per-candidate review that identifies the candidate, requested disposition, explanation, semantic assessments by evidence ID and any sourced blockers. Semantic review is an external judgment; the local code does not prove that a quote entails a claim. Do not infer a review from an empty list, malformed data, an absent item, a failed expert or pending approval.
4. **Classify conservatively:** `SUPPORTED` requires review, sufficient retrieved supporting citations, explicit semantic-support assessments for all material claims, no decisive blocker and no unknown critical coverage. `NEEDS VERIFICATION` preserves a candidate with meaningful retrievable context when review, source linkage or feasibility is uncertain. `BLOCKED` requires an identified critical restriction with retrieved matching source and explicit semantic review. `REJECTED` requires an explicit reviewed contradiction with cited retrieved evidence; retain it internally. `INSUFFICIENT EVIDENCE` applies when meaningful retrievable context is missing. Review labels alone cannot override these checks.
5. **Respond:** return at most three candidates in original order and retain the full internal record including rejected candidates. Reports show status, candidate text, why it might matter (if supplied), source references, whether each source/quote was retrieved, gaps, observed/unverified blockers and a conservative next step. Only fixed, non-executing review steps are generated by the simulator. It never performs a file write, user communication or proposed external action. The orchestrator does not convert “unknown” to “no blocker.”

The design separates lexical quote checks from semantic assessments, and treats both as weaker than external truth. The mock verifier used in unit tests is manually specified, not an independent model or real UGREEN expert. Expert-style `completed`/`failed`/`cancelled`/`waiting_user`/`waiting_approval` envelopes are **illustrative**, and real UGREEN states/fields are unverified.

## Read-only UGREEN prototype

The [prototype](/home/martelaxe/ugreen-hackathon/prototype/surprise-me/SKILL.md) asks `file-agent`, `document-agent`, and `knowledge-agent` for real scoped results and citations, then the parent produces a conservative report. It contains only Markdown; local Python is not inside the Skill and is not assumed available on UGOS. The catalog does not guarantee per-claim structured review, source excerpts or coverage, so the prototype describes a safe fallback rather than pretending those features exist.
