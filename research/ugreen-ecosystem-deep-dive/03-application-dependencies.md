# Application dependencies: files are not applications

The complete [UGREEN apps article](https://ai.ugreen.com/blogs/knowledge/top-7-nas-applications-for-performance) was read, including native apps, Docker choices, resource estimates, HTTPS, and the pre-install checklist. It stresses image/version, volumes, environment, resource limits, network exposure, backup and *test restore*. These are product instructions, **not** Uliya expert operations. NAS file storage does not grant the assistant Docker control or access to app-internal state. User-selected paths and scope are mandatory; do not read live `.env`, config secrets, vaults, keys, tokens or logs by default.

## Concrete cross-application dependency chain

Nextcloud's source-specific backup requirements illustrate the difference between “a file exists” and “the app can be restored”: at least data + config + database, plus custom apps/themes where used, must be consistent, version-appropriate and restorable. A Compose file's declaration of a bind mount does not prove the currently running container uses it; `./config` depends on the actual project base; a named volume is Docker-managed and must not be treated as an arbitrary accessible folder ([Docker storage](https://docs.docker.com/engine/storage/)). A running service is not proof backup or dependencies are healthy ([FAQ 5.2](https://community.ugreen.com/nas/pagesD/circle/post?id=1210)).

A *possible partial read-only operation* could compare an owner's **sanitized and explicitly authoritative** list of required host paths against accessible filesystem evidence, and distinguish “found”, “not observed/incomplete” and “runtime unknown”. This is a straightforward evidence report a generic agent can already perform. It does not verify named volumes, live resolved configuration, database consistency, backups, secrets, current versions or application recovery. Without the actual backup application's API and a test restore, an end-to-end claim is blocked. The previously tested [Rebuild Kit/Impact Rehearsal](../../docs/experiment-11-ai-native-nas-decision.md) and [Project Rescue](../../docs/experiment-16-project-rescue-decision.md) already explored related ground; no improvement over generic Uliya is established.

## Existing recovery tooling and real reports

- [Docker](https://docs.docker.com/engine/storage/volumes/) documents volume backup and restore; database consistency and actual runtime inputs remain app-specific.
- [Nextcloud](https://docs.nextcloud.com/server/latest/admin_manual/maintenance/backup.html), [Home Assistant](https://www.home-assistant.io/common-tasks/container/), [Plex](https://support.plex.tv/articles/201539237-backing-up-plex-media-server-data/) and [Kopia](https://kopia.io/docs/advanced/consistency/) already publish specialized backup/check/recovery procedures. A Skill needs an extra advantage, not just a checklist.
- [A self-hoster](https://www.reddit.com/r/selfhosted/comments/1tekmq8/how_do_you_verify_that_your_docker_volumes_are/) describes discovering apparently intact files did not restore a database; another [asks for a one-app GUI restore](https://www.reddit.com/r/docker/comments/1pbrjft/is_there_a_oneclick_way_to_backup_my_docker/). These are individual experiences, not measured market prevalence.
- The published [xsm-bf](https://skills.ugreen.com/us/skills/406) uses PowerShell scripts/configuration to create and verify workbench backups. [HA Git Backup](https://skills.ugreen.com/us/skills/1024) distinguishes history from encrypted recovery and uses scripts/scheduling. They demonstrate implementation complexity and competition, not UGREEN compatibility or tested safety.
