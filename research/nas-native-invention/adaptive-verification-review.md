# Adaptive verification and the observable frontier

2026-10-27. This examines the earlier local experiment and a new contrasting-workload test; none of the following measures a UGREEN NAS. [Follow-up design](../../experiments/nas-native-invention/adaptive-followup/design.md) was frozen before the fixture; raw measurements are in [results](../../experiments/nas-native-invention/adaptive-followup/results.md).

## Why the first run was not an overall performance win

The earlier G hashed 621 paths (620 files from 310 matched pairs plus one extra). S did 621 stat calls and 541 hashes, plus four listings. Its benefit came from 40 pairs with unequal sizes, whose 80 files totaled **1,699,840 bytes**—about 24.2% of the generic agent's 7,032,320 hashed bytes. For comparison, 240 identical pairs totaled 4,300,800 bytes; 30 different but equal-size pairs totaled 1,027,072 bytes. Both sides of those equal-size pairs still had to be hashed. The guided agent's exploratory duplicate hash and the generic agent's extra one-sided hash account for the small gap between 1,699,840 and the observed 1,696,256 saved bytes.

Size-first issued 543 more adapter operations overall (1,166 vs 623). Its 621 stat calls mostly did not prevent hashing: 270 same-sized pairs still needed two hashes. The 5 vs 623 outer shell calls conceal a Python client dispatching hundreds of individual operations. Such batching and concurrency were available equally to the Codex agents locally; the earlier generic agent happened not to use them. They are not documented as user-packaged UGREEN Skill execution. Two agents ran concurrently, with process startup, scheduling and page cache confounded, so 45.088 vs 37.590 seconds is an observed local result, not proof that stat overhead alone caused the difference or would occur on NAS.

## Three approaches and the key tradeoff

- **Direct:** SHA-256 both sides of each common path. Fewer separate metadata calls; hash every matched file, including obvious size mismatches. Source-only requires complete opposite enumeration.
- **Static metadata-first:** get both sizes; skip hashing unequal sizes; hash both equal-size sides. Saves bytes when length changes, and adds two metadata requests even when all lengths match. Real filesystem implementations may return size as part of listings, which would change this cost model; UGREEN does not promise such fields.
- **Adaptive sample:** sample both metadata and hashes from eight evenly spaced paths, then choose direct or metadata-first for the remaining paths using an illustrative per-stat cost of 256 KiB in byte-equivalents. This is a heuristic, not measured hardware calibration: ordering can bias the sample, file distributions can shift, and sample itself costs operations and reads. A false cost estimate can choose the wrong branch; safe classification remains the same.

The local reference trial used the same five fixture trees and in-process Python operation implementation, three rotated runs per strategy. See detailed table and log artifacts in [results](../../experiments/nas-native-invention/adaptive-followup/results.md). It found that the adaptive strategy never had the best median local time among the three; metadata-first saved hash bytes on large and mostly-different files, while direct used fewer operations on every workload. Input files were cached in an uncontrolled manner; tiny wall-time differences are descriptive, not a production estimate. Model-driven agents ran separately against a subprocess adapter and cannot be directly compared to those Python-loop timings.

The sensitivity model adds 1, 10 or 100 milliseconds to **each** observed local operation. This is an illustrative serial cost model, not a NAS benchmark or claim that UGREEN makes one remote call per item. At 10 ms the large-file example estimates 0.562 s direct, 0.733 s static and 0.868 s adaptive. At 1 ms its estimate is 0.112 s, 0.103 s and 0.130 s, respectively. The crossover depends on actual storage throughput, returned metadata, batching, caching and expert latency. Hashing a large file might execute within one expert call and data size may vary by orders of magnitude. Local in-process timings are not a substitute for calibration.

## Prior art and appropriate comparisons

[rsync's manual](https://rsync.samba.org/ftp/rsync/rsync.1) states that its default quick check uses size and modification time; `--checksum` changes the check for same-sized files. This is an established production version of staged comparison, and rsync computes internally rather than via one model-to-expert action per file. A local `rsync -n` dry-run against the different fixture flagged 78 of 102 changed paths under default quick checking and 102 of 102 with `-c`; timestamps were deliberately equal, so 24 same-size changes defeat the quick heuristic. This is a **different task/contract**, not a fair performance comparison with our SHA-256 verification, and `rsync` dry-run only reports would-transfer files, not a trustworthy global verification frontier. Logs and version are preserved.

[rclone check](https://rclone.org/commands/rclone_check/) compares sizes and hashes where available, offers size-only mode and `--download` to compare downloaded contents. Backend hash availability varies; read the command's actual results and constraints. `rclone` was not installed and was not run. Neither rsync nor rclone is proof that no comparable user-facing frontier exists; no comprehensive product search or direct human comparison was performed. The algorithms here are familiar; the only potential distinction is a truthful, interactive **per-user priority and evidence state**.

## Can UGREEN expose the frontier?

| Desired user-visible state | Documented capability | What is not guaranteed |
|---|---|---|
| What was enumerated | `file-agent` / `ug-filesystem:ls`: `path`, optional `recursive`, `max-depth`, `limit`; `find`: scoped `path`, optional filters and limit; summary mentions paths/file IDs. | Exact schema, total counts, complete/truncated flag, continuation and authoritative coverage; an unreturned path cannot be declared absent if completeness is not evidenced. |
| Which paths have metadata | `file-agent` / `ug-filesystem:stat`, required `path`, read operation; summary mentions path and time/stat. | An exact size property, batch results, returned-by-path completeness, structured error codes or stable mapping. The local adapter's size fields are test conveniences. |
| Which contents are verified | `file-agent` / `ug-filesystem:sha256sum`, required `path`; summary indicates SHA-256. | Exact digest envelope, model retaining all paired results, consistent snapshot, and proof the file has not changed since hashing. Equal hashes are practical evidence, not logical certainty. |
| What remains unknown | Parent can label missing/failed/incomplete returned evidence as unknown and relay `failed`, `cancelled`, `waiting_user`, `waiting_approval`. | A guarantee that error or truncation details actually propagate. If coverage is opaque, the unknown may be the entire scope, not a precise count. |
| What to inspect next | Parent can ask a user to prioritize known unresolved paths and delegate another supported check. | A documented cost optimizer, byte-read telemetry, strict byte budget, pause/resume cursor, stable ordering, atomic snapshots, persistent state or user interface for frontier selection. |

All child calls belong to `file-agent`; the parent requests real authorized paths and consumes returned evidence. These read actions have catalog `approval: none` yet still require actual user authorization for the selected folders. Any optional saved report or mutation is a separate authorized, appropriately approved workflow; do not assume a durable ledger, exact I/O budget or safe overwrite. The catalog describes API intent, not verified hardware behavior.

## Frontier as an interaction

A deliberately **post-hoc exploratory**, local-only probe asked to inspect at most five known common paths in the incomplete fixture. Its local adapter reported 80 known paths, source listing complete, destination listing incomplete; among the first five, four pairs got matching/mismatching actual hashes and one returned simulated denial. A second simulated user choice checked one more path, increasing content-verified pairs to five. The other known paths and unenumerated destination scope remained unknown. This is an auditable state change ([output](../../experiments/nas-native-invention/adaptive-followup/runs/frontier-probe/output.json), [operation log](../../experiments/nas-native-invention/adaptive-followup/runs/frontier-probe/events.jsonl)), not real user feedback or a UGREEN prototype.

An appropriate next suggestion is to ask whether the owner wants to restore access to the denied path or prioritize a particular unresolved pair; neither has a provable higher utility without user preferences. A *file count* cap is not an enforced disk-byte cap. A Skill might express the conversation, but there is no demonstrated generic-agent or usability advantage; reliable evidence handoffs are still the gating dependency.
