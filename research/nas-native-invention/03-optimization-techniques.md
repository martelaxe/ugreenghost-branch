# Relevant mechanisms, their limits and how to measure them

The named methods are existing techniques. A model saying “be efficient” does not implement an optimizer. Counts below are analytical and hardware-independent.

| Mechanism | How and required information | Cost avoided / measurement | UGREEN scope and prior art |
|---|---|---|---|
| Query plan + predicate pushdown | Apply cheap constraints early; database planners use statistics and cost estimates. E.g. [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) and [DuckDB](https://www.duckdb.org/docs/current/data/parquet/tips) use indexes/row-group metadata and estimates. | Avoid reading filtered records; measure bytes, rows, runtime and false negatives, including planner overhead. | A Skill may request path/type constraints via `find`; no documented stats-based planner, pushdown guarantee or model-independent execution. Semantically relevant items can have misleading names. |
| Progressive length → full hash | Group same candidate path or potential duplicates by actual size; unequal size proves bytes differ, same size needs hash. Hash equality is practical, not a logical guarantee against collision. [fdupes](https://manpages.debian.org/bullseye/fdupes/fdupes.1.en.html) already implements size+hash+byte comparison. | Hash bytes for unequal sizes can be skipped; extra stat requests may dominate. Measure SHA bytes, metadata calls and correctness separately. | `ls`, `stat`, `sha256sum` documented per path; exact stat/result fields and remote overhead unknown. This is tested locally, not a novel algorithm. |
| Hierarchical traversal | Bound exploration to authorized subtrees, track directory coverage and process complete batches. | Reduces peak context O(batch), not total Ω(N) for exhaustive inventory. Measure pages, skipped/inaccessible scopes and peak returned tokens. | `find`/`ls` depth/limit parameters exist; stable continuation and completeness signals are not guaranteed. |
| Adaptive/active evidence | Choose next question or file that could resolve uncertainty; stop when requested confidence/budget achieved and label residual unknown. | Avoid low-value reads; measure actual reads and error/recall versus exhaustive baseline. | Model can follow instructions, not a deterministic or optimal information-gain planner. Risk missing a rare critical counterexample. |
| Content-addressing/deduplication | SHA or chunk hashes identify content, often indexed in a separate database; [restic design](https://restic.readthedocs.io/en/stable/100_references.html) describes repository structures. | Avoid storing/transferring repeated bytes, but first read costs O(B); measure logical versus physical bytes. | Per-file SHA exists; no documented content-addressed index or chunk/dedup storage primitive. Exact bytes ≠ same relevance/rights. |
| Incremental snapshots / Merkle trees | Hash leaves and directory nodes to compare subtrees, assuming trustworthy cached hashes and invalidation; snapshots freeze a consistent view. [TrueNAS ZFS](https://cdn.truenas.com/docs/references/zfsprimer/) provides actual snapshot/replication capability. | Later scan can avoid unchanged subtree reads **only when** trusted persistent state and complete change tracking exist. | UGREEN Skill could save a user-approved text manifest, but cannot assume watcher, hash tree, snapshot, atomic update, permissions or authentic complete previous state. |
| Metadata-based change hints | [restic](https://restic.readthedocs.io/en/stable/040_backup.html) uses metadata rules to avoid rereading likely unchanged files, with documented tradeoffs. | Measure content read saved and missed same-size/same-mtime mutations. | `stat` may provide metadata; result specifics unknown. Report “possibly unchanged”, not verified equal. |
| Transaction planning / approval | Construct precise proposed operations, review, then revalidate paths/metadata immediately before action and verify returned results. | Fewer unsafe changes and better audit; measure incorrect proposals, partial completion and false success. | `file-workflow:start`/`run`, `cpmv`, hashes exist with appropriate approval; atomic no-overwrite, rollback and resumption unverified. Preflight is not a transaction. |
| Context and skill exposure | [SkillAlign](https://arxiv.org/html/2609.07255v1) tests full/hint/workflow renderings while holding tasks/skills fixed; [SKILL.state](https://arxiv.org/html/2608.26263v3) uses validated execution state instead of replaying history. | Potential token savings; measure actual input/output tokens and task success, not just shorter instructions. | Markdown can describe staged steps but UGREEN exposes no programmable exposure policy or validated persistent state runtime. |

## Cost and quality tradeoffs

Size-first reconciliation saves 2 hashes per unequal-size pair but adds 2 stats for each common pair. For 100,000 common paths with 10% size-mismatched, it requests 200,000 stats and 180,000 hashes instead of 200,000 hashes; whether that is faster depends on latency and sizes. If nearly all files have equal size, it adds stats and saves no reads. With incomplete listings, per-file errors or changes during examination, proof and counts can fail regardless of method. The local benchmark simulates a complete-list convenience explicitly unavailable as a catalog guarantee.
