# Large-collection bottlenecks

N = files in scope, P = same-relative-path pairs, B = bytes actually read. Costs below are explanatory models, not measured NAS costs. User permissions and directory topology matter.

| Problem / concrete situation | Scaling and failure | Existing approaches | Possible UGREEN / missing infrastructure |
|---|---|---|---|
| Enumerating 100,000 mixed files | At least Ω(N) entries must be checked to claim complete current inventory without a trusted index. Large result pages may be capped, consuming context; a missing page invalidates absence claims. | [Spyglass metadata indexing](https://www.usenix.org/legacy/events/fast09/tech/full_papers/leung/leung.pdf); [Qsirch](https://www.qnap.com/en/how-to/tutorial/article/qsirch-the-quick-start-guide) indexed search. | `find`/`ls` and explicit scopes may help; documented `limit` is not a continuation guarantee. Stable complete pagination unknown; no cataloged persistent index. |
| A small requested subset in a huge tree | Read-all text ≈ O(B) bytes plus large token context; filename/type/date prefilters can reduce reads but may miss semantically relevant files with misleading names. | [DuckDB Parquet filter pushdown](https://www.duckdb.org/docs/current/data/parquet/tips) skips row groups whose metadata excludes a predicate. | `find` documented `type`, path and date/size filters; model must report unsearched scope. No guarantee content indexing or lower latency. |
| Duplicates among backups from multiple devices | Naive all-pairs checks O(N²); grouping by byte length reduces plausible candidates, then hashes cost content bytes. Same bytes do not prove same semantic role, rights or safely removable redundancy. | [fdupes](https://manpages.debian.org/bullseye/fdupes/fdupes.1.en.html) uses size, digest and byte comparison; [Synology Storage Analyzer](https://www.synology.com/en-au/dsm/7.2/software_spec/storage_analyzer) reports duplicates with limits. | `scan-dedupe` exists but result schema is a placeholder; `stat`/`sha256sum` are per path. Never assume duplicate implies delete. |
| Partial migration of two hierarchies | Match union by path O(N); compare differing sizes without content read, equal sizes require digest to establish practical identity. Renames, metadata differences and case collisions complicate semantics. | [rclone check](https://rclone.org/commands/rclone_check/), [rsync](https://rsync.samba.org/ftp/rsync/rsync.1). | `ls`/`stat`/`sha256sum` conceptually compose, but exact size fields, complete listings and snapshot isolation are unverified. |
| Millions of records with change over time | Re-crawling each time is O(N); saved prior summaries can suggest change but mtime and size can remain unchanged while content changes, and deleted/unreadable paths are not equivalent. | [restic backup change detection](https://restic.readthedocs.io/en/stable/040_backup.html) uses a metadata heuristic; persistent indices/change feeds in purpose-built systems. | Approved `save-text` may persist a summary, but completeness, safe overwrite, verification and later readback unknown. No native event feed/watch. Do not claim trustworthy incrementality. |
| Organization and action planning | Reorganizing N files can require N moves and may break references or cause collision; a no-op plan can be safer than mass edits. | [Syncthing](https://docs.syncthing.net/users/syncing.html) handles conflicts; dedicated sync/move utilities have mature policies. | `file-workflow:start` describes plan; `run` workflow-approved. Real plan detail, collision semantics, atomicity and approval resumption are unknown. |
| Authorized scope and partial access | Search can fail or omit unreadable subtrees; an empty list must not mean complete. Different owners, inaccessible files and symlinks complicate real scope. | purpose-built file permission and backup error reporting | Skill can require explicit unknown/incomplete states; actual error/coverage envelopes not guaranteed. |
| Verification after bulk change | Changed sources, overwrites or partial writes can invalidate a plan; post-hash detects mismatch but not atomic safety or semantic harm. | [TrueNAS snapshots/replication](https://cdn.truenas.com/docs/references/zfsprimer/); software-specific consistency checks. | `stat`/`sha256sum` may help verify observed files. No documented transaction, rollback, trusted snapshot or verified no-overwrite. |
