# UGREEN capability deep dive — decision

Audited 2026-10-27. The installed Uliya Skill Creation Tool is attributable to **0.7.3** because all 26 files in the project’s `uliya-skill-kit-0.7.3-en.zip` match the installed files; the package itself has no independent version field. The catalog declares **2.0.0**, generated 2026-09-01. The authoritative local paths and source qualifications are in the [inventory](../research/ugreen-capabilities/01-source-inventory.md).

## What is really documented

There are **six distinct registered expert owners** across the installed catalog's nine CLI families: `document-agent`, `file-agent`, `knowledge-agent`, `media-agent`, `photo-agent`, and `security-monitor-agent`. There are **78 Actions**, counted once per `(CLI, Action)` pair; seven high-level capability domains are a different count. There is no cataloged `system-agent` or `ug-system` family. The [full human catalog](../research/ugreen-capabilities/02-operation-catalog.md) and [JSON](../research/ugreen-capabilities/02-operation-catalog.json) include every parameter, effect, catalog approval label, return summary and source pointer.

- **47 are labeled `read`, 27 `state-change`, and 4 `mixed`.** The mixed actions include media searches that can play and document operations that can generate/write. A read label does not guarantee complete results; a catalog approval label of `none` does not substitute for user-authorized access.
- **Meaningful actions:** file copy/move/delete and tags; workflow plans and batch operations; creation of photo albums and timelines; text saving; subtitle download; music/video playback controls. `ug-photo:timeline` is **state-changing/workflow-approved**, not simply a read. Album membership and original preservation semantics are not confirmed.
- **Approval labels:** 15 Actions are `gateway` (13 state-change and 2 mixed); 10 are `workflow`; 2 are `conditional`; 51 are `none`. User consent and child/platform approval are separate. Exact UI, atomicity, continuation and whether an approved action completed are hardware/runtime unknowns.
- **Interactive outcomes:** music search may play a song and music control includes pause, seek, speed and a stop timer; video search may play and control has pause/continue/next/previous. Camera event evidence can be requested as snapshot, clip or playback position; whether a reference can actually be opened is unverified.

Specialists can be sequenced by having the parent pass **actual verified returned information**. The strongest plausible handoffs are photo OCR text → a confirmed music search, audio transcript text → a confirmed video search, document-derived time window → a camera event query, and a real subtitle candidate → an approval-gated download. None has a fully documented, guaranteed parent-visible return schema or confirmed complete device execution. See the [composition graph](../research/ugreen-capabilities/04-composition-graph.md).

A Skill can instruct the model to keep context during a workflow and can request an explicitly approved text save. It cannot guarantee durable in-memory state across separate chats, automatic resume after approval/interruption, idempotent retries, or a persistent database. Event queries are not a subscription: no scheduled task, watcher or automatic reaction is documented. See [execution model](../research/ugreen-capabilities/05-skill-execution-model.md).

## What we underestimated and what we cannot assume

The underused native domains are **music playback**, video/subtitle lookup, **event-evidence requests**, audio transcription and cross-agent orchestration. These can produce experiences beyond text: a player starting, a selected subtitle download, a created album or an event reference. But the critical assumptions remain unresolved: exact returned IDs, whether one expert's ID works as another's parameter, user-visible playback, timestamps, file coverage, source/permission propagation, and platform approval resumption. The catalog itself contains ambiguous translations, placeholder returns, and suspicious copied enums/types; the audit preserves them instead of pretending they form a validated API.

No exposed Action implements arbitrary Python/ffmpeg, video editing, sound fingerprinting, custom HTML, a service, event watcher, new filesystem primitive or system-health/SMART query. No atomic no-overwrite guarantee exists for `cpmv`; no successful write can be claimed from a planned action or pending approval. A separate app might implement these independently, but that does not establish an allowed Skill dependency. See [boundaries](../research/ugreen-capabilities/07-boundaries-and-unknowns.md) and [underused domains](../research/ugreen-capabilities/06-underused-domains.md).

## Three end-to-end candidates

1. **Photo set list → confirmed song playback:** `photo-agent` OCR → user confirms actual line → `media-agent` searches and plays the selected track. **DOCUMENTED WITH RUNTIME QUESTIONS:** OCR and playback actions are cataloged, but exact returned identity and selecting that same track are not guaranteed. If the child cannot target it reliably, stop at a user-manual choice.
2. **Voice memo → confirmed movie playback:** `knowledge-agent` transcribes → user confirms a title → `media-agent` finds and plays the actual movie. **DOCUMENTED WITH RUNTIME QUESTIONS:** supported audio formats, transcript handoff, media targeting and playback outcome remain unknown.
3. **Training note → pet camera evidence:** `document-agent` extracts a confirmed time → `security-monitor-agent` searches user-authorized camera events and requests actual clip/snapshot evidence. **DOCUMENTED WITH RUNTIME QUESTIONS:** event-ID mapping and playable references are unknown; the final evidence step is blocked if an actual usable ID is not returned.

Each [detailed walkthrough](../research/ugreen-capabilities/10-end-to-end-walkthroughs.md) includes scope, data, delegated operations, transfer requirements, approval, actual completion and failure handling. **None qualifies as a fully documented end-to-end path**, and none has run on NAS. The most likely to function is the set-list workflow if the image and music library contain a clear exact match; this is an assessment, not measured reliability. Its step from OCR to playback is the most immediately understandable and unusual combination among these three, but [BandsManager](https://bandsmanager.com/whats-new) and [SongDeck](https://www.songdeck.studio/) describe closely overlapping photo-to-music workflows, and Uliya already markets OCR and media smart commands. The creativity claim is therefore weak, not proven. [Seven combinations](../research/ugreen-capabilities/08-supported-inventions.md) and the [competitive checks](../research/ugreen-capabilities/09-originality-check.md) show the alternatives and close prior art.

## Recommendations

**BEST UGREEN-NATIVE INVENTION:** The set-list photograph becomes one confirmed playable song. It is the best *conditional* candidate, not an established new invention or fully verified complete workflow. The next serious experiment should be a small comparison on a finalist NAS: give the same real user-selected set-list image and library to (A) ordinary Uliya and (B) a narrowly specified workflow; check OCR accuracy, exact confirmed match, actual audible playback and failure/ambiguity handling. If plain Uliya already performs it as well, or correct targeting cannot be verified, stop instead of presenting a differentiated entry.

**MOST INTERESTING MISSING PRIMITIVE:** A trusted, parent-visible **time-aligned media segment with a stable playable reference and source provenance**. If transcription, camera evidence or video analysis could reliably produce that unit and playback could target it, a stored phrase, event or visual clue could open the exact moment in the original recording. Current `segments`, camera evidence enums and player controls do not establish that end-to-end contract. This would unlock richer interactions than our current path, but cannot honestly be promised today.
