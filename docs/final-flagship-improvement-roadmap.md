# Improvement roadmap

## P0 — Before any submission

1. **User ownership, newness and eligibility review.** Confirm the entrant's eligibility and that the submitted Skill/core workflow meets the rules on development during the hackathon; compare the new package to earlier prototypes and disclose AI use. This is a human determination, not established by a filename or development date. Test: review creation evidence and [rules](https://ugreenhackathon.devpost.com/rules). Risk: an ineligible entry despite sound technical work.
2. **Review source accuracy and the exact competition package.** Inspect the PDF, referenced Markdown, checker and ZIP; ensure claims match actual experiments and device uncertainty. Test extraction, links, bytes and static checker. Risk: overselling local execution or a malformed package.
3. **Confirm the copy-role/impact core survives real returns.** Design the finalist test for paths, source excerpts, hash mapping, limits and failure states. Exact formats are unverified and are not exposed by mock tests. Test on actual assigned NAS only if selected. Risk: if citations or actual results do not propagate, output must downgrade rather than invent evidence.
4. **Resolve scope and privacy expectations.** Verify permission prompts and configured model provider/data flow with the real UI; no hidden external transfers should be implied. Risk: private material reaching an unintended model or unauthorized source being used.

## P1 — Strongest value improvements

5. **Real-owner comparison.** Invite willing NAS users to perform a comparable pre-change decision from blind ordinary/Skill outputs, including a “neither” option; measure task completion, decisions and time. This needs no new Skill capability. Risk: small synthetic examples may not represent real use.
6. **Find reliable supported coverage signals.** Verify what the actual file/document experts return on limit, missing path and inaccessible scope. Update the wording only from confirmed contracts. Risk: presumed exhaustive analysis leading to unsafe action.
7. **Improve the decisive demo.** Use the two-identical-copies fixture and real NAS returns; show the actual supporting note and unresolved purpose. No custom interface. Risk: generic Uliya may give the same answer, weakening differentiation.
8. **Inspect citation presentation.** Replace unusable host-local line references with source labels the Uliya environment really supplies; test clickable and semantic correctness. Risk: an attractive report with unverifiable evidence.

## P2 — Optional, only after core works

9. **More formats and multiple project references.** Test supported documents, symlinks, differently named versions and multilingual records with actual authorized examples; preserve ambiguity. Risk: false identity or unauthorized scope expansion.
10. **Repeat/rerun and drift comparison.** Only compare user-supplied earlier results if actual stored state and source provenance are available; no background watch or assumed persistent memory. Risk: stale review misread as safety clearance.
11. **Potential separate action.** Explore platform-supported operations independently, with user and gateway approvals, actual destination semantics and no-overwrite verification. Never add to this Skill as a promise until those contracts are established. Risk: data loss.
