# Experiment 15 decision — Readiness Delta

**STOP Readiness Delta as the standalone hackathon entry.** It is a useful advisory review but did not show a distinctive benefit over competent generic Codex with the same files and request. The most memorable proposed experience—review an earlier result, change a material permission, rerun and show PASS → FAIL—was genuinely demonstrated in a local fictional archive, but **both the generic agent and the frozen Skill did it**. A clickable, honest source trail is central to this concept; the Skill-guided reports also had serious local citation portability failures. This is a reasoned product decision, not a claim that all readiness reviews are worthless.

**One existing fallback to consider for submission: Project Rescue**, `prototype/project-rescue/SKILL.md`. It offers a more tangible owner-visible outcome: a missing project file can be recovered by one approved copy while a shared source remains. It passed static validation again, and Experiment 12 demonstrated an analogous local copy, but real UGREEN collision-safe copying, approvals and readback remain unverified; Adobe Premiere's relinking is a serious competitor. It is **not yet submission-ready**: a new review copy needs the event's required AI/third-party disclosure and a checked proposal. The [fallback outline](../submission/experiment-15/fallback-submission-outline.md) is prepared; no rejected Readiness Delta ZIP or PDF was created.

## 1. Mechanism and user experience

The idea is an on-demand **requirement → positive and contrary evidence → PASS/FAIL/UNKNOWN/NOT APPLICABLE** review of authorized stored material, with comparison to a user-supplied earlier review. Research inspiration: [metamorphic testing of changing RAG corpora](https://arxiv.org/abs/2607.26843). The paper tests how a RAG system responds to controlled corpus mutations. Our local experiment uses this as a test idea; the Markdown Skill does **not** implement the paper's mutation operators, RAG index, oracle or automatic monitoring. The user might ask: “Do these materials satisfy my stated distribution requirements, and what changed since the earlier review?” The actual output is a source-backed advisory table and a safe next action—not an enforced gate, legal certificate or proof of complete coverage.

The hypothetical value is finding a consequential change while stored files remain readable. In the local event case the illustration permission changed from public-use permission to internal-review-only. The actual [Skill delta output](../experiments/15-finalist-candidate/runs-delta/S/response.md) reported the illustration requirement **PASS → FAIL**, while the date and volunteer schedule remained PASS. It did not infer when the original file changed. The [generic delta output](../experiments/15-finalist-candidate/runs-delta/G/response.md) made the same comparison and caveat. Both were direct local Codex reads, not UGREEN calls.

## 2. Real execution and errors

- Thirty fresh local model runs covered five cases × G/S × three separate fixture waves; two more fresh G/S runs compared the same actual saved v3 baseline review to changed evidence. Same model and low effort, with prompts, logs, paths and frozen source hashes preserved. There was no huge multi-model benchmark; the extra waves were necessary after the **author's initial fixture defects** and are explicitly post-observation, not independent validation.
- In original v1, “volunteer coverage” was ambiguous. S reasonably marked it UNKNOWN; G marked baseline PASS but the irrelevant-mutation version UNKNOWN. The business example claimed a workshop had already occurred at a date in the future relative to the real review and lacked a dated current payment record; both models appropriately expressed uncertainty. Do not count that original setup as an unambiguous successful baseline.
- In corrected v3, the fictional as-of date and volunteer roster were explicit. Both G and S marked the stated event checks PASS on baseline, FAIL for the relevant permission restriction, kept the same PASS outcomes under an irrelevant stripe-color change and marked the inaccessible permission UNKNOWN. Hash comparisons confirm only one relevant or irrelevant file changed per mutation.
- Both models also passed the workshop packet checks, but the report says **invoice amount**, not explicitly **revenue**; both acknowledged that distinction while marking the revenue check PASS. This is a substantive semantic ambiguity, not evidence of reliable financial readiness. The two domains are synthetically narrow, and the second-domain result is qualified.
- In v3 reports, **43 of 82 Markdown links resolved** from their saved locations. The 43 working links were in G outputs; all 39 Markdown links emitted by S were broken. One G and one S report used plain identifiers instead of Markdown links. All 82 targets could be mapped to retained source files by a local audit, which does not establish semantic support or real NAS behavior. The G/S delta reports had 0/9 and 0/10 working raw links respectively. No automatic repair is included in the Skill.
- Eight deterministic integrity checks passed: actual Skill text in all S prompts, source hashes, exactly-one-file mutations, missing scope, unchanged originals, baseline review bytes and checker result. These checks do not establish semantic correctness or NAS runtime safety. One S output added irrelevant information about a disclosure reference missing from the **fictional data workspace**; that reference actually exists in the Skill package.

Full evidence, including the original failures and revised-wave methodology, is in [evaluation](../experiments/15-finalist-candidate/evaluation.md). Source-only workspace access was instructed and known history/project paths masked, but runtime configuration and other host paths were visible; do not claim absolute isolation. No real users were contacted or surveyed.

## 3. Official platform and competitive reality

The installed catalog documents `file-agent` discovery and reads (`ug-filesystem`), `document-agent` QA/extraction/reconciliation (`ug-document`), and optional `knowledge-agent` evidence collection and workflow-approved text save (`ug-knowledge`). The parent delegates to registered experts; it does not execute child CLIs. Actual output provenance, complete coverage, cross-format support, saved review location, non-overwrite handling, approval resumption and follow-up verification are unverified on UGREEN hardware. The optional save path was not executed in the experiment; local tool outputs must not be presented as expert returns.

Generic agents have shown the same task and the same explicit delta here. Public alternatives already cover related workflows: UGREEN's [Publish-Safe Photo Review](https://devpost.com/software/publish-safe-photo-review) classifies assets for public use, [ClaimReady](https://devpost.com/software/claimready-home-inventory) assembles source-backed evidence and gaps, [Nextcloud Context Agent](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_agent.html) offers file-aware tools, and [Adobe AEM Assets](https://business.adobe.com/uk/blog/the-latest/expand-content-access-accelerate-creation-and-improve-reuse-with-composable-services-in-adobe-experience-manager-assets) describes asset rights workflows. These are public descriptions, not hands-on equivalence tests. We have not established an exclusive capability, novel data structure or improvement over uploading the same files to a generic assistant. NAS-native access and orchestration are plausible conveniences, not proven benefits or privacy guarantees.

## 4. Judging, demo and deadline

Three fresh simulated Codex reviewers were first shown the five main cases, then rerun with the **actual** G/S delta included. In the second review, owner/engineer/creativity scores were 62/60/61 out of 100, with innovation 7/8/8 out of 25. All recommended REDESIGN and found the generic output comparable; those scores are not real judge scores. Their proposed concrete change was an explicit prior-review rerun, but both methods had already performed that test. The reviewers also did not resolve the business revenue/invoice ambiguity. Given the user's stronger novelty criterion and the actual parity, STOP is the more candid decision. [Simulated review](../research/15-finalist-candidate/judge-review.md).

The [90-second storyboard](../research/15-finalist-candidate/demo-plan.md) could show a user-approved initial review and a manually requested rerun after a relevant source update, if real device source access, approval, saved review and citations work. No custom dashboard, background monitoring or actual release gate is available. Judges could reasonably reject this as a competent generic document review with a PASS/FAIL table; this is the most likely product objection.

Official [rules](https://ugreenhackathon.devpost.com/rules) and [event requirements](https://ugreenhackathon.devpost.com/) set Round 1's deadline at **November 15, 2026, 11:45 p.m. Pacific**, requiring a PDF proposal and Markdown Skill ZIP, but no NAS demo. Round 2 requires the same project to run on the assigned NAS. Readiness Delta is **not recommended for Round 1**. No PDF, ZIP, SkillHub publication, Devpost submission, commit or push was made.

**Single next action:** make a new disclosure-compliant review copy of Project Rescue, then re-run the official checker and prepare its real-device no-overwrite/approval test plan before treating the fallback as ready for entry. The existing prototype and earlier experiments must remain unchanged.
